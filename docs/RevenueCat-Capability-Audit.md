# RevenueCat capability audit

_Checked 26 September 2026 against the Lumi’s Lab code and the live RevenueCat project._

## What is in place

The SwiftUI app uses the RevenueCat and RevenueCatUI Swift Package products. Debug builds use the RevenueCat Test Store. The project has `monthly` ($4.99), `yearly` ($39.99), and `lifetime` ($79.99), all attached to `lumis_lab_pro`. One current `default` offering contains all three packages and has a [published Lumi’s Lab Plus paywall](https://app.revenuecat.com/projects/c4ecf93e/paywalls/pwc5915bbca73d4f61/builder). The app fetches `CustomerInfo`, observes updates, checks the entitlement, displays the paywall behind a parent challenge, handles purchase and restore outcomes, and opens `CustomerCenterView` for renewing subscribers.

The live project currently has **one Test Store app, one offering, one paywall, no experiments, no targeting rules, and no webhook integrations**. Audience configuration could not be audited because the connected RevenueCat API key lacks the audience read scope. The only playable room, Glass Pond, is currently free; no playable content uses `lumis_lab_pro` as an access gate. This makes the purchase flow demonstrable, but does not yet demonstrate a real Plus unlock.

## Best next demonstrations

| Capability | Concrete Lumi’s Lab use | What it adds |
| --- | --- | --- |
| **A real Plus unlock** | Keep the main Glass Pond lesson free; add a finished bonus challenge or room that unlocks when `lumis_lab_pro` is active. Route a parent who asks to unlock it through the existing challenge before showing a paywall. | Shows the entitlement changing actual app behavior, including after restore or expiration. Do not advertise unbuilt rooms as available benefits. |
| **[Placements and targeting](https://www.revenuecat.com/docs/tools/targeting/placements)** | Define `parent_settings` and `locked_room` placements. Fetch the offering for each placement, with a default-offering fallback, and use a rule to give them distinct parent-facing paywall copy. | Demonstrates context-aware, remotely controlled offers. Keep purchase paths behind the parent gate; avoid collecting a child’s behavior for targeting. Targeting requires Pro or Enterprise. |
| **[A/B experiment](https://www.revenuecat.com/docs/tools/experiments-v1/experiments-overview-v1)** | Duplicate the current offering, attach a second paywall, and compare the current three-choice design with a version that explains the yearly value more clearly. Keep the same products and prices so the test isolates the design. Set up a draft experiment using the two offerings; use a customer offering override to preview each variant. | RevenueCat assigns the offering variant server-side. This app already fetches the customer's current offering, so a basic offering experiment needs no new purchase code. Experiments require Pro or Enterprise. |
| **[Multipage paywall](https://www.revenuecat.com/docs/tools/paywalls/creating-paywalls)** | Give parents a short “what Plus unlocks” screen before the plan picker, with localized product prices on the final screen. | Shows RevenueCat’s remote paywall editor beyond a single purchase page. An exit offer would require a separate offering and a supported SDK presentation method: it will not run from this app's manually embedded `PaywallView` sheet. |
| **[Customer Center retention](https://www.revenuecat.com/docs/tools/customer-center/customer-center-configuration)** | Add a cancellation-reason survey and, after real App Store products exist, a relevant promotional offer for eligible subscribers. Keep restore, refund, and plan-change help in the parent area. | Goes beyond merely presenting `CustomerCenterView`. Promotional offers must first exist in App Store Connect; Customer Center requires Pro or Enterprise. |
| **[Paywall and subscription analytics](https://www.revenuecat.com/docs/dashboard-and-metrics/charts)** | Review paywall encounter, abandonment, conversion, LTV, churn, and Customer Center survey responses. Optionally send paywall interaction and lifecycle events to a product analytics service. | RevenueCat Paywalls record impressions automatically. Analytics integrations can add close, cancel, and component-interaction events. Meaningful comparisons require production traffic. |
| **[Webhooks](https://www.revenuecat.com/docs/integrations/webhooks)** | Send subscription lifecycle events to a verified backend endpoint for support records or adult-facing renewal/billing communications. | Demonstrates server-side lifecycle handling. This requires a backend and a Pro plan; the app should still use `CustomerInfo` for local access decisions. |

The most convincing compact demo is a **real Plus-gated bonus activity**, the parent-gated paywall, two placement-specific paywall variants, a draft A/B experiment, and Customer Center. RevenueCat can assign test customers to variants, but [iOS Simulator/Test Store purchases and paywall views are excluded from experiment conversion and revenue results](https://www.revenuecat.com/docs/tools/experiments-v1/experiments-results-v1). Do not present synthetic test activity as a measured A/B winner.

## Before a real-money release

The project has only a Test Store app. Create the actual App Store subscriptions and lifetime purchase, connect the App Store app and public Apple SDK key, and test with Apple’s sandbox. Replace the paywall's plain-text Terms and Privacy labels with working destinations. Confirm that every advertised Plus benefit is shipped. [Test Store keys are for debug builds only](https://www.revenuecat.com/docs/test-and-launch/sandbox/test-store); RevenueCat rejects them in release builds.

If adult accounts are added later, use stable, non-guessable App User IDs and RevenueCat login to carry entitlements across devices. The current anonymous identity is appropriate for the present single-device prototype. See [Identifying Customers](https://www.revenuecat.com/docs/customers/identifying-customers).
